# 单房间 AI 改造助手重构设计

日期：2026-10-16
状态：生成流程、工作台交互与服务端校验已在对话中确认；待书面规格审阅

## 1. 目标与边界

用户在 `http://127.0.0.1:8000/console` 的某个已完成房间 Scan 中，请小助手根据该房间的结构、家具、尺寸和正式风险提出多个整改选择。每个选择必须有可执行的空间编辑、改造后的框架视图、简短说明和可核查的量化变化。用户可以对比后保存一个方案。

本轮只维护工作台入口。整屋 Scan、Flutter 报告页均不接入新生成流程。整屋场景没有整屋风险评分，本助手不得把单房间结果表述成整屋结论。既有正式报告、扫描产物和点云保持只读；所有改造在内存沙盒中计算。

方案属于空间模拟，不承担承重、水电、施工许可、现场尺度复核等判断。不可评估指标保持不可评估，不得写成已经改善。

## 2. 现状与选择

当前工作台的“AI 改造模拟”先让用户勾选风险，`/solve` 为每个指标单独搜索编辑，随后把编辑合并交给 `/simulate`；另一条自由文字路径由规则解析。它们最终只给出一组结果，须保存后才能进入现有方案 3D 页。`assistant/local_llm.py` 是可选的本机措辞接口，未参与候选生成。现有 `scheme3d.mjs` 和 `build_scheme` 已分别提供前后布局渲染及正式链路重算能力。

考虑过三种生成方式：

1. DeepSeek 单轮输出三组编辑：响应快，但有效方案数量不稳定。
2. DeepSeek 输出候选，服务端验算；不足时把冲突与未改善原因反馈给模型修订一轮：采用此方案，可控制延迟并提高有效率。
3. 让模型循环自主搜索：覆盖面更广，但调用次数、耗时和结果可追溯性难控制。

模型只负责提出不同改造思路与编辑，不产生展示用分数。正式计算链路决定可行性、数值和风险变化。

## 3. 用户流程与界面

房间工作台顶部的“小助手”入口进入 `#/scans/{scan_id}/assistant`。房间未完成、缺结构或测量时展示明确的不可用原因。页面默认依据该房间当前可评估的主要风险生成方案；用户可以补充一段不超过 300 字的改造目标。生成期间显示进度和取消页面请求的操作。

生成完成后，左侧列出最多三张可切换候选卡，中央共用一幅交互式 3D 家居框架图，右侧或下方展示所选候选的证据。每张卡包含：

- 方案名、设计意图、具体编辑动作和是否涉及施工或假设新增物体；
- 改造前后正式分数、关键指标值与风险等级，数据不足时显示相应状态；
- 来自扫描的事实依据、模型提出的原因、服务端验算结论及模拟边界；
- “查看改造前/后”切换和“保存此方案”动作。

切换候选时直接使用该候选的 `layout_before` / `layout_after` 更新同一 3D 视图；未保存的候选也能完整预览。沿用 `scheme3d.mjs` 的墙、门、窗、家具框与改动标记，保留旋转、缩放、重置视角。选中方案后才持久化；方案库与已有方案详情页继续可用，保存后的描述与证据在详情页可读。旧的“勾选风险→单次模拟”面板从工作台移除，工作台不再调用 `/solve` 作为生成入口。

小屏时先显示方案卡与关键信息，3D 视图保持可操作、无横向溢出；按钮可用键盘访问，选中状态与改造前后状态不能只靠颜色表达。视觉沿用工作台现有主题与语义色。

## 4. 服务端契约

新增 `POST /api/assistant/scans/{scan_id}/proposals`，请求体为可选的 `goal` 字符串，最多 300 字。沿用 `get_org_scope`，只允许读取所属机构的已完成单房间 Scan。后端加载该 Scan 的 `measurements.json` 与优先的 `structure_calibrated.json`（缺失时使用 `structure.json`），构造精简上下文：房间尺寸、家具及开口的稳定 ID 和几何、可评估的风险与阈值、当前评分。不给模型发送视频、图像、点云或账号资料。

通过 DeepSeek 的 Chat Completions API 调用 `deepseek-flash`，请求 JSON 输出。系统提示约束模型：只引用已提供 ID，返回三种不同取舍的方案，每组包含标题、意图、结构化 `edits` 和引用的风险代码；禁止编造实测值、分数、施工结论。使用后端环境变量 `DEEPSEEK_API_KEY`；模型、接口地址、超时和令牌上限可配置，密钥不进入前端响应、日志、数据库或 Git。默认接口为 `https://api.deepseek.com/chat/completions`。官方接口资料见 [初次调用](https://api-docs.deepseek.com/) 与 [JSON 输出](https://api-docs.deepseek.com/guides/json_mode/)。

实机生成时，服务端在调用模型前尝试有限数量的空间编辑，包括小幅门宽调整、逐件移除及对各家具轮流尝试移动，使用同一个候选校验器筛出最多四个不同操作目标的 `verified_starters`，只把其编辑和相关风险代码送入上下文。菜单至少有两项时，提示模型为每项选择一个不同的 starter，原样复制编辑并自行写标题与设计意图；菜单不足两项时不限制模型自行提案。菜单只提供模型可选输入，不直接成为返回方案；模型回复仍须逐项独立验算，不足两个可信方案时仍返回失败。

响应返回 `scan_id`、`input_fingerprints`、`proposals`（最多三项）和生成状态。每项包含临时 ID、标题、设计意图、`edits`、`layout_before`、`layout_after`、`applied_edits`、`comparison`、`metric_changes`、`risk_changes`、`evidence`、`limitations` 与 `disclaimer`。`evidence` 中的数值由服务端从正式链路计算，明确来源指标；AI 原话只作为设计意图。所有候选的几何和数值来自同一次 `build_scheme` 结果，避免卡片与 3D 图不一致。

## 5. 候选校验与修订

服务端先按严格结构解析模型 JSON，只允许当前沙盒与框架渲染器都支持的编辑操作，例如家具移动、移除、假设新增、90° 旋转和门宽调整。目标 ID 必须存在，数字必须有限且在房间尺度及配置限额内；不接受模型输出的任意文件路径、URL 或执行指令。每组至少有一项有效编辑。

对每组候选执行 `build_scheme(measurements, structure, edits)`。发生几何冲突、编辑未实际生效、关键指标变得不可评估、整体风险恶化或完全没有可核查改善的候选不作为推荐方案。按规范化编辑与改动对象去重：仅把同一家具挪动不同厘米数而风险变化相近的结果视为同一策略。有效候选优先保留不同改造对象、操作与改善目标；每组的评分和描述都基于其独立模拟结果，绝不把多个候选编辑合并成一组分数。

首轮少于两组有效且有区别的候选时，向模型发送一次结构化失败反馈，请其修订或补足，不泄露内部异常堆栈。第二轮后若仍不足两组，接口返回明确的“当前资料/房间条件下不足以生成多个可信方案”及原因；不填充未经验证的卡片。目标是提供 2–3 个选择，而非保证每个房间都有三种可行改法。

模型超时、鉴权失败、配额不足、空内容、坏 JSON 或服务端校验失败时，界面显示可重试状态和合适的原因；不得悄悄回退到旧求解器并冒称 AI 方案。请求和修订各有明确超时，页面离开后不保存生成结果。

## 6. 持久化与旧数据

继续用 `renovation_schemes` 存储所选方案的 `edits`、输入指纹和来源，新增一个 JSON 元数据字段（通过 Alembic 迁移）：方案标题、经过长度限制的设计意图、引用风险代码、服务端生成的证据摘要与限制。保存接口必须重新验证编辑和输入指纹，防止生成后扫描数据已变仍保存旧结果。读取方案时按现有机制报告 `stale`；旧记录没有元数据时仍能展示编辑、评分和框架图。

不删除历史方案，也不改造正式扫描数据。旧 `/solve`、`/simulate` 可在迁移期间保留兼容调用，但工作台新入口不调用它们；不再把它们描述为新小助手的生成路径。`assistant/local_llm.py` 的本机措辞能力不接入新流程。

## 7. 验证标准

1. 对同一个已完成房间，生成至少两组独立、无冲突且有可核查改善的候选时，工作台可逐张切换，3D 改后布局与各自 `edits` 一致。
2. 每组卡片的分数、指标、风险变化等于服务端从该组 `edits` 单独运行 `build_scheme` 的输出；不可评估指标不出现改善承诺。
3. 模型返回不存在的 ID、越界数值、重复策略、坏 JSON 和未改善候选时，校验与至多一轮修订按约定生效，不泄露密钥或内部堆栈。
4. 缺少数据、跨机构访问、整屋 Scan、模型不可用分别得到明确错误；其他机构看不到该房间的候选和方案。
5. 保存后在方案库和详情页可见描述与证据，原有方案仍能正常读取，过期输入继续标记。
6. 键盘可选候选、切换前后视图与保存；窄窗口不遮挡主要操作。后端测试使用替身模型响应，不消耗真实 API 配额；另做一次受控的真实接口冒烟验证。
