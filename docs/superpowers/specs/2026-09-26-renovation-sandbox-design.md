# 改造沙盒：可视化布局与同源评分设计

日期：2026-09-26
状态：已与产品负责人逐段确认，待评审后进入实施计划

## 1. 背景：现在为什么是黑箱

现有"AI 安全改造助手"（`backend/app/routers/renovation.py` + `backend/pipeline/renovation_simulator.py`）存在两个问题。

**问题一：勾选建议给出的是"许愿分"，不是算出来的分。**
`_project_completed_suggestions()` 直接把目标风险等级改写成 `low`，再用正式权重重算总分。几何操作（把某件家具挪 N 厘米）只决定"动了什么"，完全不参与评分。

**问题二：自由改造用的是另一套指标引擎。**
`pipeline/renovation_geometry.compute_metrics()` 是独立实现的栅格 + OBB 指标引擎，与正式链路（`space_foundation` → `spatial_assessment_inputs`）不是同一套代码。在 scan 46 真实数据上，15 项正式指标有 6 项对不上：

| 指标 | 正式值 | 沙盒引擎值 |
| --- | --- | --- |
| activity_area | 4.384 | 9.883 |
| main_passage_width | 0.72 | 0.846 |
| minimum_passage_width | 0.48 | 0.50 |
| path_length | 1.36 | 2.55 |
| crowding | 0.5309 | 0.5468 |
| entrance_space | 2.163 | 2.158 |

而界面展示的"改后分"是 `正式分 + 沙盒引擎算出的 delta` 拼出来的。同时，改后的布局从来不返回前端，用户看不到房间变成了什么样。

**实锤：现有建议经官方链路验证后大面积不成立。**
把当前代码生成的 4 条顶部建议逐条喂给官方链路（scan 46，基线 80.0 分）：

| 现在的建议 | 目标指标 | 风险等级 | 总分 |
| --- | --- | --- | --- |
| 床边活动空间不足 | 0.30 → 0.103（更糟） | high → high | 80.0 → 80.0 |
| 通道最窄净宽 | 0.48 → 0.48（无变化） | high → high | 80.0 → 80.0 |
| 门净宽 | 0.846 → 0.90 | medium → low | 80.0 → 82.7 |
| 空间拥挤度 | 0.531 → 0.452（仍超标） | medium → medium | 80.0 → 84.0 |

"床边净空"那条之所以把指标改得更糟：它选中了离床最近的书架，发现书架已经贴墙（`_wall_blocked`），于是按"反方向移动"的兜底逻辑把书架朝房间内推了 0.40m——正好推近床边。

**可行性已验证。** 官方链路是纯内存函数，对 scan 46 重算 15 项指标与 `spatial_metrics.json` **零差异**、总分精确复现 80.0，单次耗时约 0.03 秒。搜索式求解跑几百个候选只需数秒。

## 2. 目标与非目标

**目标**

1. 用户能看到"采纳建议后的房间布局"（2D 叠影图 + 3D 效果），而不是只看到一句话和一个分数。
2. 改后分数**同源**：与正式报告走完全相同的链路，在内存副本上重算。
3. 建议**先求解再给出**：每条建议对应一份被验证过能达标（或明确说明无法达标）的布局方案。
4. 用户能自己编辑布局（拖动、移除、新增、撤销、旋转 90°），实时看到指标与分数变化。
5. 方案可保存、可命名、可多方案对比、可导出 PNG 与 PDF 附录。

**非目标**

1. 不改动正式报告、实测评分、点云、视频、图像与扫描产物——全部只读。
2. 不做自由角度旋转（只提供 90° 吸附旋转）。
3. 不做分享链接（外链只读权限、失效控制、跨机构隔离成本高于收益；导出图片已覆盖分享场景）。
4. 不做施工可行性判断（承重、水电、插座位置不在模型内），文档与界面均声明"仅为空间模拟"。
5. 不重写正式评估链路，也不重构 `pipeline_runner` 的产物生成方式。

## 3. 核心设计决策

**决策一：唯一真源。**
所有改后指标与分数都由 `analyze_structure_passages → build_spatial_foundation → build_spatial_assessment_inputs → build_risk_assessment` 在内存副本上计算。沙盒自带的指标引擎退出评分，仅保留其几何辅助能力（定位瓶颈、生成候选方向），不再产生任何展示数值。

**决策二：只存编辑记录，不存结果。**
方案 = 一串 `edits` + 输入哈希。派生状态（改后的房间、家具、开口）每次现算，保证方案可审计、可重放、可复现。

**决策三：建议必须求解 + 验证。**
对每条风险做候选搜索，每个候选跑一次官方链路，取"达标且改动最小"的解；无解时返回"最接近但未达标 + 差距"，不虚构提升。

**决策四：一套几何，四处复用。**
同一份 `SchemeState` 同时喂给评分、2D 叠影图、3D 盒子、导出，不存在第二个真相。

**决策五：屏幕与导出一致。**
2D 图由 Flutter 端一套绘制代码渲染（`CustomPainter`），屏幕显示与导出的 PNG 使用同一套绘制逻辑，避免"屏幕一个样、PDF 另一个样"。

## 4. 数据模型

### 4.1 编辑记录（唯一可写对象）

```json
{
  "id": 12,
  "scan_id": 46,
  "name": "方案A · 书架沿墙下移",
  "created_by": 7,
  "created_at": "2026-09-26T18:20:00Z",
  "updated_at": "2026-09-26T18:20:00Z",
  "based_on": {
    "measurements_sha256": "…",
    "structure_sha256": "…"
  },
  "source": "solver",
  "edits": [
    { "op": "move", "target": "bookshelf_001", "dx": 0.0, "dy": -0.90 },
    { "op": "remove", "target": "storage_rack_001" },
    { "op": "add", "label": "箱子", "size": [0.6, 0.4, 0.5], "center": [0.8, 0.4, 0.25], "assumed": true }
  ]
}
```

- 家具一律用 `instance_id` 引用，禁止用数组下标。
- `op` 取值：`move`（dx/dy，单位米）、`remove`、`add`（`assumed` 恒为 true）、`rotate`（仅 90° 的整数倍）、`resize_door`（放宽门洞）。其中 `rotate` 只由用户在编辑器中触发，`resize_door` 只由求解器生成——编辑器不提供改门洞的入口，因为那属于施工而非摆放。
- `add` 的物体在派生状态中带 `assumed: true`，在结果卡、叠影图、PDF 中统一标注"假设放置，非实测"。
- `based_on` 记录输入哈希。若扫描后处理产物变化导致哈希不匹配，方案标记为"基于旧数据"，读取时明确提示，不静默按新数据重算。

### 4.2 派生状态（只读，每次现算）

`SchemeState = apply(edits, measurements, structure)` 返回：

- `room`：`{ bounds_xy, height_m, floor_polygon }`
- `openings`：门、窗（含门宽改动）
- `objects`：家具与障碍物（含新增、移除、位移、旋转后的结果）
- `assumed`：新增物体的标记集合
- `applied_edits`：真正生效的编辑（被约束拒绝的不在其中）

派生状态再进入官方链路得到 `metrics`（15 项）、`risks`、`overall`、`category_scores`。

### 4.3 求解结果（不落库）

```json
{
  "metric_code": "bedside_clearance",
  "risk_name": "床边活动空间不足",
  "solved": true,
  "edits": [{ "op": "move", "target": "bookshelf_001", "dx": 0.0, "dy": -0.90 }],
  "before": { "value": 0.30, "level": "high" },
  "after": { "value": 0.55, "level": "low" },
  "score": { "before": 80.0, "after": 85.0 },
  "shortfall": null,
  "requires_construction": false,
  "evaluations": 41,
  "elapsed_ms": 1240
}
```

无解时 `solved=false`，`edits` 为"改善最大"的候选，`shortfall` 说明仍差多少（例如"仍差 0.10m，只能通过移除书架或更换薄型家具达成"）。

### 4.4 持久化

新增表 `renovation_schemes`（Alembic 迁移，开发/测试可由 `AUTO_CREATE_TABLES` 建表）：

| 列 | 说明 |
| --- | --- |
| id | 主键 |
| scan_id | 外键 → scans.id，索引 |
| name | 方案名，默认"方案A/B/C…" |
| edits | JSON |
| based_on | JSON（输入哈希） |
| source | solver / manual |
| created_by | 外键 → users.id |
| created_at / updated_at | 时间戳 |

机构隔离通过 Scan → Project → org 校验，不冗余 org_id。方案不落工作目录，因为 `data/work/{scan_id}` 会被重跑覆盖。

## 5. 接口契约

全部挂在 `/api/assistant/scans/{scan_id}/`，鉴权与机构隔离沿用 `get_org_scope`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/suggestions` | 风险列表 + 每条"能否求解"的预判（不跑求解，秒回） |
| POST | `/solve` | 入参 `{metric_codes: []}`；返回求解结果数组（见 4.3） |
| POST | `/simulate` | 入参 `{edits: []}`；返回改后 layout、15 项指标、风险等级、总分、变化明细、约束冲突 |
| GET | `/schemes` | 方案列表（含分数摘要） |
| POST | `/schemes` | 保存方案（入参 name + edits） |
| GET/PATCH/DELETE | `/schemes/{scheme_id}` | 读取 / 重命名 / 删除 |
| GET | `/schemes/{scheme_id}/layout.json` | 改后布局，形状与现有 `layout.json` 一致，供 3D 查看器 |
| POST | `/schemes/{scheme_id}/export.pdf` | 接收客户端渲染的 PNG（multipart），返回方案附录 PDF |

**`POST /simulate` 的关键约定**

- 无状态：不写库、不写工作目录、不修改任何真实文件。
- 传空 `edits` 时返回的分数必须等于正式报告分（同源证明的可执行断言）。
- 响应固定包含 `scope: { simulation: true, raw_media_accessed: false, structured_inputs_only: true }`。
- 约束冲突（穿墙、重叠、超出房间）不报 500，返回 `conflicts: [{type, targets, overlap_m}]` 与修正后的状态。

## 6. 后端流程

### 6.1 输入加载

只读 `data/work/{scan_id}/postprocess/` 下的 `measurements.json` 与 `structure_calibrated.json`（缺失时回退 `structure.json`）。缺任一即返回 409，与现有行为一致。

### 6.2 求解器

1. **定位相关家具**：按风险对应的 metric_code 决定候选集合——瓶颈位置的家具、参与该项指标计算的对象，以及距目标区域最近的 1–3 件可移动家具。
2. **候选生成**：每件候选家具 × 4 个轴向 × 步长 0.1m，最大位移不超过房间对角线；另外生成"移出房间（remove）"候选。对门宽类风险额外生成 `resize_door` 候选（放宽到 0.90m），该候选标记 `requires_construction: true`，界面必须与"搬家具"类方案区分显示。
3. **约束过滤**：房间边界内、与其他物体 OBB 不相交、不遮挡门洞（遮挡则标注为冲突但仍可评估）。
4. **评估**：每个候选在内存副本上跑官方链路，读取目标指标与总分。
5. **选择**：优先"目标指标达标且位移最小"；同等条件下优先不需要施工的方案（`requires_construction` 为 false）；无达标候选时选"改善最大"的候选并计算 `shortfall`。
6. **预算**：最多 300 次评估；超预算返回当前最优并在响应中标注 `budget_exhausted: true`。

求解器不做旋转搜索（旋转仅由用户在编辑器里手动触发 90°）。

### 6.3 模拟器

`/simulate` 复用同一套 `apply + 官方链路` 流程，不做搜索，只算给定 edits 的结果，供编辑器高频调用（前端 150ms 防抖）。

### 6.4 与现有模块的关系

- `pipeline/renovation_simulator.py` 中的 `_project_completed_suggestions()`（许愿式投影）与独立指标评分路径**删除**。
- `_suggestion_op` 的启发式操作**不再直接产出方案**，仅可作为求解器的候选生成提示之一；其结果必须经官方链路验证后才可展示。
- `pipeline/renovation_geometry.py` 的几何工具（栅格、瓶颈定位、OBB 距离）保留复用，但其 `compute_metrics`/`payload_from_geometry` 不再产生展示数值。

## 7. 前端交互

### 7.1 报告页（甲：看结果）

助手卡片改为三段：

1. **建议列表**：每条风险显示当前值、风险等级与达成标签——`可达成（移动家具）` / `需把家具搬出房间` / `需施工（改门洞/换门）` / `无法达成`。勾选后点"生成方案"触发 `/solve`，显示求解进度。
2. **方案结果卡**：2D 叠影图 + 分数条（80.0 → 85.0）+ 指标变化 + 风险等级变化；动作：`进入沙盒编辑` / `保存为方案` / `导出 PNG` / `导出 PDF`。
3. **自由改造输入框**：保留自然语言输入，解析为 edits 后走同一条 `/simulate`，与勾选建议不再有两条评分路径。

### 7.2 视觉语言（叠影对比）

- 原位 = 灰色虚线幽灵框；新位 = 实心框（蓝色表示本次改动，灰色表示未改动）。
- 位移用虚线箭头连接原位与新位中心，并在旁标注距离（如"↓0.90m"）。
- 被移除的物体保留幽灵框并加"已移除"标签。
- 新增物体用橙色实心框 + "假设放置"标签。

### 7.3 沙盒编辑器（乙）

- **手机竖屏（全屏编辑器）**：顶栏实时分数；中间平面图画布；底部选中对象操作条（±10cm 方向键、旋转90°、移除、复位）+ 改动清单。
- **横屏 / 网页**：左图 + 右侧 15 项指标联动面板（红/黄/绿，点击任一项显示触发规则）。
- **拖动**：拖动时本地即时预览，松手后 150ms 防抖调用 `/simulate`。
- **吸附**：贴墙（≤5cm 自动贴）、邻近家具边线对齐、10cm 网格。
- **约束反馈**：撞墙或重叠时红色描边 + 弹回 + 提示（如"与床重叠 0.12m"）。
- **选中信息**：尺寸、离墙距离、与最近家具间距。
- **撤销/重做**：编辑记录栈，支持一键重置回原始布局。
- **3D 看效果**：WebView 打开查看器并带 `scheme` 参数；保留原始点云，原位画灰色虚线线框盒，新位画实心盒；默认叠影态，一颗播放按钮在同场景内播放"家具从原位滑到新位 + 分数滚动"的动画。不做左右双视图。

### 7.4 多方案对比

方案卡片横排：缩略叠影图 + 总分 + 涨幅 + 改动摘要，最优方案打"最优"标签；点开卡片查看该方案的指标明细。不做横向矩阵表与双方案滑块。

## 8. 导出

- **PNG**：客户端离屏渲染叠影图（与屏幕同一套绘制代码，3 倍分辨率）；页脚固定标注"沙盒模拟 · 非实测"、扫描名、日期、分数。
- **PDF 附录**：客户端上传该 PNG，服务端封装为独立文档（标题、对比图、指标变化表、风险变化、声明、输入哈希）。正式报告 PDF 不变，方案 PDF 是另一份文件。
- 不实现分享链接。

## 9. 数据边界与安全

- `/simulate`、`/solve`、`/schemes` 只读 `measurements.json` 与 `structure_calibrated.json`，不读视频、图像、点云、SLAM3R 或 SpatialLM 中间产物。
- 所有响应带 `scope` 声明；模拟只在内存副本上进行，不写回任何真实产物。
- 正式 `spatial_metrics.json`、`risk_assessment.json`、报告与 PDF 保持只读，实测分数永不被覆盖。
- 方案按机构隔离，跨机构访问返回 404。

## 10. 测试与验收

| 项 | 验收标准 |
| --- | --- |
| **同源证明** | scan 46 上官方链路内存重算的 15 项指标与 `spatial_metrics.json` 逐项零差异；总分等于 80.0；`/simulate` 传空 edits 的分数必须等于报告分 |
| **复现性** | 任一已保存方案重新计算，分数与展示时的完全一致 |
| **求解器** | 已知可解风险（拥挤度、门宽）必须返回达标解；已知无解风险（门宽不足且只能移动家具）必须返回 `solved=false` + `shortfall`，不得伪装成功 |
| **约束** | 穿墙、重叠、超出房间的 edits 必须被拒绝或修正，并在响应中给出 `conflicts` |
| **数据边界** | `/simulate` 只读两类结构化 JSON（scope 断言 + 文件访问断言双重验证） |
| **机构隔离** | 跨机构访问方案返回 404 |
| **画布一致性** | Flutter 绘制的几何与后端 layout payload 一致（黄金样例测试） |
| **编辑交互** | 拖动约束拦截、吸附、撤销/重做、重置的组件测试 |
| **导出** | PNG 非空且含声明文字；PDF 可打开且含对比图与指标表 |
| **端到端** | scan 46：求解 → 保存方案 → 重开 → 对比 → 导出，全流程通过 |

基线约束：后端既有测试集的 4 个已知失败（见 `docs/risk-assessment-baseline.md`）不得增加；新增测试必须全绿。

## 11. 分期

**阶段一（甲：结果闭环）**

1. 抽出内存态官方评估入口，`/simulate` 改为同源计算并返回 layout 与指标。
2. 求解器 + `/solve`。
3. `renovation_schemes` 表与方案 CRUD。
4. 报告页方案结果卡 + Flutter 叠影图绘制。
5. PNG 导出 + PDF 附录。

**阶段二（乙：可编辑沙盒）**

6. 全屏编辑器（拖动、吸附、约束、撤销、旋转 90°、新增、移除）。
7. 横屏/网页的指标联动面板。
8. 多方案卡片对比。
9. 3D 查看器叠影与播放动画。

阶段二复用阶段一的全部数据结构、求解器与渲染代码。

## 12. 风险与取舍

| 风险 | 说明与对策 |
| --- | --- |
| 求解可能给出激进方案 | "把家具搬出房间"在几何上最优但在生活中未必可行；界面用 ⚠️ 标签区分，最终由用户判断 |
| 每次拖动都算 | 单次 0.03 秒，配合 150ms 防抖足够；拖动过程中先本地预览，不阻塞交互 |
| 求解上限 300 次评估 | 复杂房间可能触及预算；超预算时明确标注，不假装已找到最优解 |
| 新增物体无实测证据 | 统一标记 `assumed: true`，界面与导出均标注"假设放置，非实测" |
| 输入数据被重跑 | `based_on` 哈希不匹配时提示"基于旧数据"，不静默重算 |
